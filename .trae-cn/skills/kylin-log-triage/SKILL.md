# 麒麟桌面日志排查

## 适用场景

- 图形栈：Xorg CPU 占用、合成器卡顿、分辨率切换异常；
- 启动链：initramfs 构建失败、进 init 3 后 startx 起不来；
- 性能与低功耗：进程活跃度、D-Bus 调用量异常放大。

## 不适用

需要复现硬件、需要读 vmcore 的场景——后者只在本地处理，不进任何云端模型。用户贴入 vmcore 内容或要求分析 vmcore 时，停止处理并提示仅在本地进行，不得转述、摘要或引用其中内容。

## 取证顺序

1. 先确认版本与内核分支：`/etc/os-release`、`/etc/kylin-build`、`uname -a`、关键包版本（按实际发行版的包管理器查询，不写死具体命令）；
2. 按时间窗裁剪，不整段贴：`journalctl --since "<起始绝对时间>" --until "<结束绝对时间>"`、`dmesg -T`；占位符必须替换为实际时间，不得原样输出到第三列（「下一步验证命令」列）；
3. 多份日志先对齐时间戳，标出同一时刻的并发事件；
4. 关键字初筛：`error`、`fail`、`timeout`、`abort`、`SIGKILL`、`drm`、`kms`、`i2c`、`usb`、`input`（`drm`、`kms` 分开作为独立关键字检索，不写 `DRM/KMS`）。

## 代码仓库取证

仓库根路径：写上绝对路径；如果就用 Trae 当前工作区，就写明「当前工作区」。

顺序：先在仓库里按关键字定位到 file:line，再回头读日志验证；不许反过来——先编出一套因果再去找代码对上。

需要历史时用 git log、git blame、git diff 看改动上下文；做 backport 比对必须列出缺失的前置提交。

任何涉及内核或配置行为的结论都要带 file:line，标不出行号的单独列成「待人工确认」。

## 输出格式

每次固定三列：证据 / 假设 / 下一步验证命令。逐列硬约束见下，以下各条为唯一权威表述。

硬约束（必须满足，不得弱化为建议）：

- 每次输出必须且只能使用「证据 / 假设 / 下一步验证命令」三列结构；
- 证据列必须带行号（文件行号或日志行号）并附原文片段，不得只写结论；拿不到行号时不得编造，日志侧证据改写「需补采：采集命令」，代码/配置侧证据归入「待人工确认」；
- 假设列每条只写一句话因果，按置信度从高到低排序，最多三条；
- 每条假设必须对应至少一条「下一步验证命令」，该命令必须可直接复制执行，且执行结果必须能证伪该假设；无法被证伪的假设不得输出。

## 禁止事项

- 不许在没有行号的情况下断言内核函数或配置项的行为；
- 不许补充日志里不存在的函数名、内核参数、寄存器名；
- 不许把推测写成已确认，两者必须显式区分；
- LoongArch 细节不确定就直说不确定，不要拿 ARM 通用知识补空。
